⚡ Parallelization analysis

Task 1 (scaffold) is a hard prerequisite for everything — no test harness or dev server exists before it. Fixed after review: Task 2 (types + chapter manifest + router) must land before Tasks 3/4/5/6 start, not alongside them — every one of those tasks' own test files imports a concrete symbol Task 2 creates (CHAPTERS from src/data/chapters.ts for Task 3, VisualizerStep/ ChapterMeta/ComplexityRow from src/types.ts for Tasks 4/5/6) — none of those modules exist until Task 2's steps create them, so a subagent starting Task 3/4/5/6 from the post-Task-1 base alone hits an unresolved-module error instead of the intended TDD red/green cycle. Once Task 2 has merged, Tasks 3, 4, 5, and 6 touch disjoint files and have no dependency on each other's output, so they run in parallel together. Chapter 03 assembly (Task 7) depends on all of 3/4/5/6 finishing, so it must come after. The build-verification task must be last.

  • Batch 2: Task 2 alone (types + chapter manifest + router) — touches src/types.ts, src/data/chapters.ts, src/App.tsx, src/main.tsx, src/pages/ComingSoonPage.tsx. Must finish and merge before Batch 3 starts — it's the shared dependency every other task's tests import from.
  • Batch 3: Tasks 3, 4, 5, 6 in parallel, once Task 2 has merged — Task 3 (layout shell) only touches src/components/layout/*; Task 4 (visualizer engine) only touches src/components/visualizer/*; Task 5 (content components) only touches src/components/content/*; Task 6 (BST diagram + step data) only touches src/chapters/03-trees-bst/*. No file overlap between any pair, and each only consumes types/data Task 2 already produced.
  • Batch 4: Task 7 (Chapter 03 page assembly) — needs Task 3 (ChapterLayout), Task 4 (Stage), Task 5 (ConceptCard/ComplexityTable/Quiz/ChapterNav), and Task 6 (TreeDiagram + steps) all merged first. Also updates src/data/chapters.ts (mark chapter 03 available: true with its route) and src/App.tsx (register the route) — both touched by Task 2, so Task 7 must start after Task 2's changes are merged, not run concurrently with it.
  • Batch 5: Task 8 (production build verification) — must run last, after everything is merged.

Critical path (longest sequential chain): Task 1 → Task 2 → Task 7 → Task 8 (4 tasks deep — Task 2 gates Batch 3 but Batch 3's own tasks aren't on the critical path since Task 7 needs all of them done anyway). Tasks that share a file and therefore cannot run in parallel: Task 2 and Task 7 both edit src/App.tsx and src/data/chapters.ts — Task 7 must wait for Task 2's version of those files, not branch from scratch.

🛠 Implementation plan

For agentic workers: use superpowers:subagent-driven-development or superpowers:executing-plans (or plan-pro's parallel execution). Steps use checkboxes for tracking.

Goal: Ship a working Vite+React+Tailwind static site for the DSA Study Deck with a reusable layout/visualizer engine and one fully content-complete chapter (03 · Trees & BST).
Architecture: A chapter-agnostic shell (icon rail + topbar + non-sticky visualizer stage + centered doc column) driven by a small chapter manifest; each chapter supplies its own diagram renderer and step data through a generic useVisualizer hook and Stage component, so adding chapter 04+ later means writing chapter-local files only, never touching the shell.
Tech Stack: React 18, Vite 5, TypeScript 5, Tailwind CSS 3 (tokens consumed as raw CSS custom properties from design-tokens/tokens.css, no theme-extend duplication), react-router-dom 6, lucide-react, Vitest + React Testing Library + jsdom.
Global Constraints (from spec.md — apply to every task):
  • Static output only — vite build → dist/, no server/backend/database anywhere.
  • Icons: lucide-react only, colored via currentColor/CSS token — never a hardcoded hex, never AI-generated.
  • Colors: consume design-tokens/tokens.css custom properties directly (e.g. var(--color-accent)) — never hardcode a hex that duplicates a token.
  • --color-highlight (amber) is reserved for "current step / you are here" only — never reused for a different meaning in any new component.
  • Typography: JetBrains Mono for code/labels, IBM Plex Sans / IBM Plex Sans Thai for body — self-hosted via @fontsource/* imports in src/index.css (Task 1), never a CDN link (spec §7: the site must work offline from disk).
  • Chapter manifest must stay data-driven — no chapter gets a hardcoded nav entry outside src/data/chapters.ts.
  • Ponytail discipline on every new-code step: before writing a step's implementation code, run the ponytail ladder (YAGNI → stdlib → native → dependency → one-liner) — this is a scaffold-and-content plan with mostly small, isolated units (a hook, a data file, a presentational component), which is exactly ponytail's proactive-trigger shape per this project's global rules. Skip it only for the few steps that are genuinely algorithm-shaped or already minimal (e.g. the BST step-array port in Task 6, which is a 1:1 data port, not new logic). Mark any deliberately-skipped simplification inline as {/* ponytail: <reason> */} rather than silently adding complexity.

import { useCallback, useEffect, useState } from 'react';
import type { KeyboardEvent } from 'react';
import type { VisualizerStep } from '../../types';

/** Mirrors design token `step-control.autoplay-interval` (--step-control-autoplay-interval: 1200ms).
 *  Kept as a number because setInterval needs ms, not a CSS string — change both together. */
const PLAY_INTERVAL_MS = 1200;

export function useVisualizer(steps: VisualizerStep[]) {
  const [index, setIndex] = useState(0);
  const [playing, setPlaying] = useState(false);
  const last = steps.length - 1;

  const goTo = useCallback((i: number) => setIndex(Math.max(0, Math.min(last, i))), [last]);
  const next = useCallback(() => setIndex((i) => Math.min(last, i + 1)), [last]);
  const prev = useCallback(() => setIndex((i) => Math.max(0, i - 1)), []);
  const reset = useCallback(() => setIndex(0), []);
  const togglePlay = useCallback(() => setPlaying((p) => !p), []);

  useEffect(() => {
    if (!playing) return;
    const id = setInterval(() => {
      setIndex((i) => {
        const n = Math.min(last, i + 1);
        if (n === last) setPlaying(false);
        return n;
      });
    }, PLAY_INTERVAL_MS);
    return () => clearInterval(id); // ponytail: effect cleanup owns the id, no timerRef needed
  }, [playing, last]);

  /** spec §5: shortcuts are scoped to the stage element (attach via onKeyDown on a tabIndex=0
   *  element), never window — so `space` on a focused quiz option still answers the quiz.
   *  Space is also left alone when a button inside the stage has focus, so a focused chip/control
   *  activates normally instead of being hijacked into play/pause. */
  const onKeyDown = useCallback((e: KeyboardEvent<HTMLElement>) => {
    if (e.key === 'ArrowRight') next();
    else if (e.key === 'ArrowLeft') prev();
    else if (e.key === ' ' && (e.target as HTMLElement).tagName !== 'BUTTON') { e.preventDefault(); togglePlay(); }
    else if (e.key === 'r' || e.key === 'R') reset();
  }, [next, prev, togglePlay, reset]);

  return { index, step: steps[index], total: steps.length, playing, next, prev, reset, goTo, togglePlay, onKeyDown };
}

/** spec.md §5 narration markup: only **bold** and `code`. One regex split, real elements, no innerHTML.
 *  Capturing group keeps the delimiters in the split output so we can classify each piece. */
const MARK = /(\*\*[^*]+\*\*|`[^`]+`)/g;

export function renderNarr(text: string): ReactNode[] {
  return text.split(MARK).map((part, i) => {
    if (part.startsWith('**') && part.endsWith('**')) return <strong key={i}>{part.slice(2, -2)}</strong>;
    if (part.startsWith('`') && part.endsWith('`')) return <code key={i} className="mono text-[12px]">{part.slice(1, -1)}</code>;
    return part;
  });
}
